# Changelog

Notable changes to agent-surface and its first-party MCP services. Format: [Keep a Changelog](https://keepachangelog.com/); the repo is pre-1.0 and unreleased changes land on `main`.

## [Unreleased]

### Added

- **Trae CLI user rules** - user installs now write the per-rule files to `~/.trae/rules` with their scoped references, as project installs do; before, user installs wrote no rules. With an offline prompt render (placeholder model, no sign-in), `traecli` 0.207.1 and 0.209.1 inline the always-apply rules and list the glob-scoped ones on demand. Neither reads the international IDE's `~/.trae/user_rules.md`, so a joint `trae,trae-cli` install does not give the CLI the rules twice.
- **Pi MCP wiring** - Pi 1.3.0 reads MCP servers from `~/.pi/agent/mcp.json` and, in trusted projects, `.pi/mcp.json`. Synapse and Grimoire now merge into its `mcpServers` like the other JSON hosts, keeping any servers already there, so 25 hosts are wired. On Pi 1.3.0, `pi mcp list --json` connected both generated user entries and listed all eleven tools. Pi's default `codemode` exposure is kept: the tools are callable from codemode scripts and are not declared to the model. Whether a Pi agent uses them in a task is not measured.
- **Grok Build user instructions** - user installs now write the always-on rules to `~/.grok/AGENTS.md`, which Grok loads as global instructions outside folder trust; before, only project installs carried them. On grok 1.0.62, `grok inspect --json` lists the installed file with `scope: global` and its exact size. Project installs keep the shared root `AGENTS.md`, which Grok loads only once the folder is trusted.
- **Held-out Grimoire retrieval gate** - the 52-request relevance set that confirmed any-term search, written without sight of the index and graded blind by two raters, is now a CI test over all five served packs. It holds a useful skill in the top five for at least 85% of covered requests and a direct one for at least 80%; the shipped reader measures 40/42 and 30/33, and the conjunctive reader it replaced fails at 11/42.
- **Four starred skill repositories as pinned externals** - `tech-leads-club` (92 tech-leadership skills) is an opt-in Grimoire source-pack served as `tech-leads-club:<name>`. Grimoire now discovers skills nested under category folders at any depth, stops at each skill root, reports later same-name duplicates as skipped, and fails the build when a requested pack yields no skills. `open-code-review` (only `open-code-review-delegate`, which drives the `ocr` CLI and needs no model backend), `no-ai-slop` and `diagram-design` are opt-in development skill-packs, shipped in the npm package with their licenses.

- **Grok Build native agents** - `grok-build` now writes the six subagents to `~/.grok/agents` or a project's `.grok/agents` with `--category development`. Each access tier becomes Grok's typed `capabilityMode` narrowed by a `tools` allowlist, with no MCP inheritance, no pinned model and no `permissionMode`. Grok already loaded Claude Code's `.claude/agents` copies, where, per Grok's source, `permissionMode: plan` does nothing and the worker's `bypassPermissions` turns on always-approve; in the same directory the native files now win. On grok 1.0.46 the parent delegates to them by type, a child runs on the parent's model, a read-only child has no write tool and no child reaches MCP tools. grok 1.0.44 lists them but runs every delegated task as its built-in `general-purpose` agent, so delegating to them needs 1.0.46.
- **Target notices in plans, builds and `doctor`** - `install` plans, `build` and `doctor` now print lifecycle, security and compatibility notices stored per target in `registry/target-capabilities.json`: Antigravity's workflow format retiring on 2026-10-19, DSH requalification after CVE-2026-82533, the unmaintained OpenHands V1 CLI, and Devin Desktop's removal of the Cascade harness plus Cascade's rule-size limits. A plan that writes manual-only skills under a workspace `.agents/skills` also gets a derived notice, because Antigravity discovers that directory and documents no manual-only metadata. Notices never block and are never written into generated files. `check` validates the notice records.
- **Static-analysis Grimoire pack (Trail of Bits)** - registers the `semgrep`, `codeql`, and `sarif-parsing` skills from the Trail of Bits static-analysis plugin as an opt-in `source-pack` served just-in-time by Grimoire as `trailofbits-static-analysis:<name>`, closing the SAST gap the `lint-*` skills leave open. It indexes the plugin's `plugins/static-analysis/skills` subtree only, so the other Trail of Bits skills stay reference-only, and the pack is skipped without error when the submodule is absent. Semgrep and CodeQL are external prerequisites the operator installs; the skills do not auto-install CodeQL or upload SARIF. Content is CC BY-SA 4.0, carried in the pack attribution.
- **Browser automation MCPs (Playwright, Firefox DevTools)** - adds two opt-in general browser MCP entries so a host can drive a real browser beyond the Chrome-only `chrome-devtools`. `playwright` (Microsoft Playwright MCP, pinned) is the cross-engine option: it drives Playwright's own downloaded Chromium headless with `--isolated` so no profile is written to disk, and the browser is fetched by Playwright itself (pre-provision with `npx playwright install chromium`, `--with-deps` on Linux, or let the first tool call download it). `firefox-devtools` (Mozilla-hosted Firefox DevTools MCP, pinned) adds native Gecko/Marionette depth, launched headless with `--tool-preset slim` so the default `evaluate_script` tool is not exposed, against a fresh profile with `--connect-existing` omitted; the detected Firefox is passed as `--firefox-path`. Both are uncategorized and installed only when named with `--service`, so the development category and the synapse+grimoire baseline are unchanged; `chrome-devtools` stays as the Chrome performance-trace specialist.
- **`ops-pentest-report` engagement-report skill** - writes the client-facing deliverable for an authorized security engagement as one self-contained document: identity block with authorization and test window, dual-audience executive and technical layers, a `F-NNN` finding register whose identifiers are immutable across revisions, CVSS v4.0 published as score plus full vector, CWE for the weakness class and CVE only where a public instance exists, ATT&CK technique per confirmed action, coverage stated so absence cannot be read as safety, retest status that distinguishes re-tested from reported-fixed, cleanup disposition, and hash-referenced redacted evidence. Companion references carry the fixed section order with conditional modules (segmentation, compliance mapping, social engineering, detection and response) and the per-finding field set with severity bars. It obeys the reporting law already in `rules/04-cybersecurity.mdc` rather than restating it, and refuses to author a report whose written authorization cannot be named. Registered in the cybersecurity asset category, so it ships only under `--category cybersecurity` and never lands in a default install.
- **SOP and runbook authoring in `ops-docs`** - the standalone type table gains a product SOP / operational runbook genre with a companion template: one controlled-document profile carrying document ID, approver, effective date, review cadence, and records retention, and a lighter runbook profile that keeps only owner and last-verified date. Both share a body where every step states its action, its exact command, and the expected result that proves it worked, plus verification against an observable world state, rollback or an explicit irreversibility boundary, and escalation criteria. Closes the gap where `ship-deploy` checked runbook parity but nothing in the distribution authored the runbook.
- **Native Windows for the first-party MCPs** - synapse and grimoire install from a portable Node installer (`mcps/<name>/install.mjs`, `npm run install:<name>`) instead of a POSIX shell script, so native Windows runs the same registry recipe as macOS and Linux rather than reporting the service unavailable. The launcher is written in each platform's idiom: a `#!/bin/sh` script where there is a shebang, and a `.cmd` shim on Windows where there is not — which makes it executable under PATHEXT, still matches the registry's extensionless `~/.local/bin/<name>`, and is launched through the wrapper's cmd.exe routing. Both pin the absolute Node the installer version-gated and re-check the >=22.17 floor at launch, so a host with an older Node first on PATH gets a named error instead of a crash inside `node:sqlite`. The always-on sidecar service stays macOS-only (launchd); Linux and Windows use the bridge's existing lazy autostart, and that autostart no longer flashes a console window on Windows. Synapse's `~/.synapse` directory is restricted to its owner by ACL on Windows, where POSIX mode bits are inert — the bearer token, the discovery file that carries it, and the memory databases with their WAL/SHM siblings would otherwise be readable by every account on the machine.
- **MCP credential env-delivery** - `install` collects each service's declared credentials into a scope-appropriate `.env` (interactive prompts for required keys, headless fails closed; values never enter host config or logs). The file is owner-only by the mechanism the host actually enforces: mode `0600` on POSIX, and on Windows an explicit ACL (inheritance dropped, the owning user granted) because Windows ignores mode bits entirely — if that cannot be applied the install warns, naming the file. Servers that declare credentials launch through a shared env-loader wrapper (materialized into `~/.local/bin` during install with the install-validated Node pinned) that loads the installer-resolved `.env` (ambient env wins) then execs the real command with stdio + working directory preserved; keyless servers keep their direct launch. `.env`/`.env.*` are excluded from Git and the package.
- **Selected-MCP prerequisite provisioning** - `install` detects (read-only) each selected MCP service's executable prerequisites and runtime floors — resolving each binary to an absolute launch path (an existing directory or non-executable file is not accepted as a launch binary) and wiring that absolute path into the generated launch command (including inside the credential wrapper's args), so a tool installed into a directory the host does not have on PATH still launches instead of failing with `spawn <name> ENOENT` — and establishes only what is missing before it wires any host config. Only the services a run will actually wire are provisioned, so a category-filtered install (skills only, say) is never blocked by an MCP prerequisite it does not use. Recipes pick the actual installer for the environment: macOS Homebrew, Linux apt/dnf/pacman/zypper, Windows winget, with the uv standalone installer as a fallback. The executor re-resolves each recipe command against fresh detection before running it, so a prerequisite installed earlier in the same run (e.g. uv into an off-PATH `~/.local/bin`) is invoked by its absolute path — a single `install` bootstraps uv and then uses it, with uv never on the caller's PATH. Chrome DevTools gets a browser on every supported distro: Debian/Ubuntu and Fedora/RHEL install Google Chrome from Google's repo, while Arch and openSUSE install Chromium (Chrome has no official package there); the provisioned browser's absolute path is passed to the server as `--executablePath`, so it drives exactly the browser that was detected rather than relying on channel auto-discovery. A server whose resolved launch binary defers to `#!/usr/bin/env <interp>` (npx, and the MCP bin npx spawns) is launched through the shared wrapper, which puts the install-validated Node at the front of that child's PATH — so the whole npx → MCP → browser chain starts under a host's minimal PATH instead of failing with `env: node: No such file or directory`. The wrapper hands over the credential env-file only to servers that declare credentials, and servers launching a real binary or absolute-interpreter script (synapse, grimoire) keep their direct launch path. OpenOSINT is provisioned through uv with its provider extras (shodan, censys, openai, ollama), which are detected inside OpenOSINT's own interpreter so an already-installed launcher never masks missing extras; Censys is probed as `censys.search` because that distribution installs a PEP 420 namespace package, so a bare `censys` resolves against any directory of that name on `sys.path` and read satisfied with the client library absent. Native Windows follows the same rules in its own idiom: executability is decided by PATHEXT (a POSIX-style extensionless path such as `~/.local/bin/uv`, or any non-PATHEXT file, is not a launchable binary and never reads satisfied), a bare command resolves to its `.exe`/`.cmd` through PATHEXT and still matches its registry name, and the wrapper is the install-pinned `node.exe` invoked with the launcher module rather than a shell stub — there is no shebang on Windows, and a `.cmd` wrapper would be unspawnable by the Node-based hosts that make up nearly all of them. npm's `.cmd`/`.bat` console shims (npx, and the recipe commands themselves) are run through `cmd.exe` with per-token quoting, so a `C:\Program Files (x86)\…` path survives intact; `Path` is extended in place rather than shadowed by a second `PATH`. A tool's environment directory is resolved by asking the tool (`uv tool dir`) instead of assuming a layout — uv's differs per platform and is redirectable, so a hard-coded path reported a successful install as missing extras — Windows bootstraps uv through Astral's standalone installer (which targets a declared detect path, keeping the same-run bootstrap closed) rather than a WinGet portable package that lands off the running process's PATH, and an authorized install carries that authorization into WinGet (`--silent --disable-interactivity --accept-package-agreements --accept-source-agreements`) while still declaring that its machine-wide installs need OS elevation. Prerequisites with no runnable recipe on the current platform are reported unavailable rather than run through an unsupported recipe; every prerequisite in the registry now carries one for all three platforms. Interactive installs ask once, `-y` authorizes, headless never prompts, and `--dry-run` only shows the plan. A service whose required prerequisite cannot be established — unauthorized, declined, or unsupportable on this platform — is skipped without wiring while the rest of the install proceeds and the run reports non-zero with guidance; its existing config is preserved and completed prerequisites are reused on re-run. One unavailable MCP server therefore never blocks a user's skills and rules, and only the services a run actually wires are provisioned at all. The MCP-package Node floor (≥22.17) is tracked separately from the root CLI floor (≥20.12).

### Changed

- **Grimoire search matches any query word instead of every one** - FTS5 reads space-separated terms as a conjunction, so one word a skill's text happened to lack discarded it before ranking: "configure tls 1.3 for a service" lost the TLS skill on `service`, and a model that expanded a working query with a plausible extra word lost its answer. Terms are now OR-ed and filler words are dropped, leaving weighted BM25 to order the candidates, so a word a skill lacks no longer excludes it. Alternatives joined by `/`, `,`, `;` or `|` (`tls/ssl`) count as separate terms, while `.` and `-` keep a version or CVE ID together, and an all-caps name such as `CAN` or `IT` is never treated as filler. Over the 30 reviewed queries against the pinned cybersecurity pack, hit@1 goes 19/30 to 23/30, hit@5 0.800 to 0.967 and MRR 0.711 to 0.836, and seven sentence-shaped queries that previously returned nothing relevant now all land in the top 5. The regression floors rise to 0.85 hit@5 and 0.75 MRR, above the conjunctive behavior they replaced. The deliberate cost: a query no skill covers used to return nothing and now returns its nearest lexical matches, so the tool description and api-contract state that hits are ranked candidates a caller must judge against its own task, not a verdict that one fits.
- **Review findings are judged by real impact** - the always-on workflow rule now has agents judge each review finding's priority themselves instead of adopting the reviewer's label. A non-blocking finding is fixed or answered with a one-line pushback without another review round, and re-review follows only a fix to a real blocker, such as a correctness, security, or data-loss defect. Where the user or repository policy makes a review a blocking gate, or a commit-only workflow forbids patching findings, those rules govern instead.
- **`ops-swarm` picks sub-models by tier and adds Droid** - the runtime catalog now opens with a role-to-tier procedure (`frontier`, `workhorse`, `fast`, `independent`) and, per runtime, how to list current models, use a latest alias, and record the model a session actually ran, so an orchestrator resolves current IDs instead of trusting a dated row. The 2026-10-15 snapshot adds Droid exec (tier aliases such as `openai-latest-fast`; read-only by default; custom droids only at `--auto high`), moves Codex to GPT-6 and Claude Code to Opus 5.5 and Sonnet 5.5, follows Cursor's renamed Grok 4.7 IDs, and replaces the retired `deepseek-v4-flash:0731` Ollama model. The launch reference gives each runtime a read-only and a writing packet shape plus one worker-lead prompt, and `droid`, the existing workflow runtime name, joins the swarm and BOSS runtime lists.
- **Distributed skill packs carry their upstream license** - a skill-pack's optional `license_file` is delivered as `LICENSE` into every distributed skill directory that does not ship its own, so the Sanyuan, CTF, red-team boundary, OCR delegate, no-ai-slop and diagram-design skills now arrive with their MIT or Apache-2.0 notice. `notice_files` carries further upstream notices under their own names, such as diagram-design's third-party icon licenses.
- **Grimoire serves each skill's own license and author** - frontmatter `license` and `author`/`metadata.author`, plus any license file in the skill root, are kept per skill (index schema 3) and appended to the pack attribution on `grimoire_get` and `grimoire_file_get`, because a catalog such as Tech Leads Club mixes CC BY 4.0, MIT and third-party terms. Rebuild with `npm run install:grimoire`; a server still running the old schema reports `INDEX_STALE` until its host restarts it.
- **Windsurf (legacy Cascade) leaves `--target all`** - `windsurf` is now a deprecated compatibility target. `build --target all` and `install --target all` list it as excluded and leave its installed files and manifest as they are, and `build --target windsurf` reports it as not buildable, because build renders the full user-scope rules and those exceed Cascade's limit. `install --target windsurf` still works for an existing Cascade install, but refuses before writing anything (`OUTPUT_LIMIT_EXCEEDED`) when the selected rules file exceeds Cascade's documented limit: 6,000 characters for the global rules file and 12,000 for a workspace rule file. A project-scope general install fits; user-scope rules and any development rules do not, so leave rules out there with `--category skills,commands-as-workflows,external,mcps`. agent-surface adds no Devin target: Devin CLI 3000.11.3 already lists the rules, skills and MCP servers of the targets `all` keeps through its default imports, each skill found in several roots once per source under a prefix such as `/claude:ops-nuke` (listing only; no signed-in task was run).
- **Trae splits into three targets by the roots each product reads** - `trae` now covers the Trae international IDE (`~/.trae` with `user_rules.md` and skills, the documented `~/.trae-cn/agents`, and MCP in `mcp.json` beside the IDE's per-OS `User` settings, written once the IDE has run), `trae-cn` the CN IDE (`~/.trae-cn`) and `trae-cli` Trae CLI 2.0 (`~/.trae/traecli.toml`, `~/.trae/agents`, and `~/.trae/skills`, which it co-owns with `trae`). Both IDE editions share the project `.trae` paths. `--target trae` no longer writes the CN IDE's rules or the CLI config: after upgrading, `trae` keeps the `~/.trae-cn/user_rules` files and `traecli.toml` servers the combined target wrote, claimed and untouched, until `trae-cn` or `trae-cli` itself claims each file or server; `trae` then lets go of it without removing or pruning it. Install those targets where you use them. Trae CLI 1.0's `~/.traecli` copies (project ones included) are removed, servers merged into a user `~/.trae/mcp.json` that neither the macOS nor the Windows IDE build reads are pruned, and projects no longer get an unread `.trae/user_rules.md`.
- **Cline per-IDE MCP files only where Cline is present** - the VS Code, Cursor, Windsurf and Devin Desktop per-IDE `cline_mcp_settings.json` routes, which the pre-SDK Cline extension most installs run reads, are merged only when that IDE's extensions folder holds the Cline extension. Plans list skipped routes with the reason, and an unreadable extensions folder blocks the plan. Earlier installs created the file for every IDE; the next full install prunes the servers agent-surface merged into a route whose IDE has no Cline and leaves the file otherwise untouched. That full install also resets optional services on the routes it keeps, as full installs always do, so rerun your `--service` installs afterwards. Devin Desktop, the renamed Windsurf, gets its own route under its `Devin` user-data folder, live when `~/.devin/extensions` holds Cline, so an install does not create Devin's user data ahead of Devin's first-run migration from Windsurf; Cline that Devin loads only from the legacy `~/.windsurf/extensions` gets no Devin route. The shared `~/.cline` route, which the CLI and Cline's SDK-based extension read, is unchanged.
- **Zed and Goose config follows each OS's documented directory** - on Windows, user installs now write Zed's `AGENTS.md`, scoped rule references and `settings.json` MCP merge under the profile's roaming AppData directory (`%APPDATA%\Zed` by default), and Goose's `config.yaml` MCP merge under `AppData\Roaming\Block\goose\config`, instead of `~/.config/zed` and `~/.config/goose`, which the Windows clients never read. As for VS Code, the directory is resolved from the profile home and a redirected `%APPDATA%` is not followed. macOS and Linux keep `~/.config`. On Windows, the next full install prunes the old `settings.json` and `config.yaml` servers and removes the old personal `~/.config/zed/AGENTS.md` and scoped rule references. A personal `%APPDATA%\Zed\AGENTS.md` you wrote yourself blocks the Zed install as `UNOWNED_DESTINATION` until you move it. The Windows routes are not natively qualified; the Windows CI job plans them.
- **Poolside personal instructions follow the documented `AGENTS.md`** - user installs write `~/.config/poolside/AGENTS.md` instead of `~/.config/poolside/.poolside`. An install that writes the new file retires the old one with it, since the current client reads both and would load the rules twice; a narrower selection than the one that wrote `.poolside`, such as `--category rules` after a development install, stops instead of dropping that contribution. The personal `AGENTS.md` needs pool 1.0.7 or later, the release that switched to it from `.poolside`; older builds read only `.poolside`, so plans carry a `POOL_AGENTS_MD_CLIENT_FLOOR` notice: update pool first, or keep a copy of `.poolside` on an older build. Poolside honors `XDG_CONFIG_HOME`, which agent-surface does not follow.
- **Capability claims narrowed to what each host documents** - for Codex, Copilot, Cursor, Kimi Code, Kiro, OpenCode, Pi and VS Code, the capability registry, adapter READMEs and target reference now name the product unit the target covers (CLI, IDE extension, editor profile or engine), which config homes are and are not followed, scopes that exist only through `--dest`, and how far each claim is proven. Codex rules and VS Code MCP are user-scope only, Kimi Code settings and hooks no longer claim a project file Kimi does not document, Cursor's home-directory rules are marked unverified because Cursor documents only project rules and settings-based User Rules, and Cursor CLI is claimed only for MCP and project rules. Kiro plans now carry a `KIRO_MANUAL_STEERING_AUTOLOADED` notice: every generated Kiro agent loads all steering files, the manual workflow files included, and Kiro's docs disagree on whether Kiro CLI honors inclusion modes, so where that matters, install Kiro without `--category development`, and without `--category private` when its local command overlay exists. No generated output changes.
- **Install respects every owner in the install root** - `install` reads ownership from every `<target>-manifest.json` in the root's `.agent-surface/`, from `legacy-owned.json` and from legacy nested manifests, instead of the target's own manifest alone. An existing file no manifest claims is the operator's: the plan refuses it as `UNOWNED_DESTINATION`, identical bytes included, rather than overwriting it or adopting it into a manifest, so move or remove it and rerun. A file several targets own is regenerated for the requested selection, and the plan lists `SHARED_CONTRIBUTION_REPLACED` when that drops a category another target recorded. Stale cleanup keeps a file while any other target still claims it. An unreadable manifest blocks as `MANIFEST_UNREADABLE` instead of aborting or being ignored. Before the first write, each target's manifest is extended with every path the run will touch, so an interrupted run can be rerun to finish. Every target that writes the workspace `AGENTS.md` at project scope now renders one target-neutral header, so `--target all --scope project` no longer conflicts over that file. The credential template `.env.example` is likewise replaced only when it is absent or an earlier install generated it.
- **Bumped the `hack-skills` Grimoire pin to 103 skills** - advanced the pinned `hack-skills` source pack five commits (`c9a4b9e` to `6fbf0bc`), which adds the `attack-surface-mapping` recon skill (102 to 103) and folds a security-engineer-ops doctrine into the `hack` master skill. Reviewed as an authorized-content change: the update strengthens the start gate (written authorization or refuse), adds explicit destruction boundaries, keeps weaponized detail in deep skills, and introduces no secrets or live infrastructure.
- **Removed the `snapshot` npm script and the `settings`/`plugins` inventory counters** - `npm run snapshot` was a byte-for-byte alias of `npm test` with no snapshot directory behind it, and the two counters only ever reported empty placeholder directories. `npm test` and `npm run inventory` are unchanged otherwise.
- **Curated external portfolio** - keeps strong large skill catalogs in Grimoire, retains evaluated references as source-only submodules, and removes thirteen duplicate or unnecessary checkouts. Karpathy guidance is no longer mirrored because canonical workflow/project rules own the behavior; Sanyuan development distribution now keeps only skill authoring and review.
- **Runtime/model routing refresh** - replaces the June model table with current Codex, Claude, DeepSeek, Grok, Cursor, Kimi, and Ollama Cloud recommendations; refreshes headless command shapes and prefers driver-native subagent or agent-manager tools before subprocess orchestration.
- **`ops-clean` simplification gate** - requires a concrete reduction in owners, layers, dependencies, configuration axes, or failure modes instead of counting rearrangement or raw line changes as simplification.
- **`ops-docs` skill** rewritten to the Diátaxis + minimalism model: aggressive, repo-fit, and concise by default.
- **Document-genre routing** - `ops-docs` now names the shared standalone identity block as a contract that genre skills extend rather than rename, and both `ops-docs` and `ops-report` state which skill owns which artifact: status report for discussion, traveling document, or authorized-engagement security report. Five report outlines previously coexisted with no statement of ownership.
- **README** rewritten lean (203 → ~100 lines); the full target matrix moved to `docs/reference/targets.md`.
- **Full-access policy ownership** - Kilo and OpenCode full installs replace the complete permission object with wildcard allow while preserving unrelated top-level settings; category-only MCP installs do not alter host-wide permission or sharing controls.
- **Node floor raised to 20.12** - the installer's credential resolution uses the built-in `util.parseEnv`; `engines.node` now declares `>=20.12.0` to match (Node 18 is EOL and was already untested in CI).

### Fixed

- **Synapse on FastMCP-proxied hosts** - OpenHands 1.16.0 (with two or more MCP servers) and Deep Agents Code 0.1.86 mount servers through FastMCP's proxy, which advertises MCP roots and then answers `roots/list` with an error, so Synapse's bridge failed startup on both while Grimoire connected. The bridge now honors `SYNAPSE_ROOTS=ignore`, which skips roots and keys the project by cwd, and rejects any other value. The installer sets it only where the host is verified to start the bridge in the workspace: the OpenHands user config, where Synapse keys the project by the launch directory (a session whose `OPENHANDS_WORK_DIR` names another directory needs `SYNAPSE_PROJECT`), and Deep Agents project configs not rooted at the home directory. Every other host keeps the fail-closed roots negotiation, and a Deep Agents user-scope Synapse still does not connect, because dcode starts user-level servers in its server's work directory. Natively, OpenHands listed 11 tools for the generated pair and a Deep Agents project config connected Synapse.
- **Qoder and Qwen Code no longer let the model start manual workflows** - both list a custom Markdown command among the skills the model may invoke unless its frontmatter sets `disable-model-invocation`, and the generated commands did not, so `ops-nuke`, `ship-deploy`, `ship-release`, `ship-commit` and `boot-facade` were model-invocable. Each generated command now sets `disable-model-invocation: true` and stays a slash command. Qwen Code 0.25.2 marks a flagged command not model-invocable and its schema has accepted the key since 0.22.3; Qoder 1.1.73's Skill tool refuses a flagged entry. Read from each CLI's shipped code and listings; no model session was run.
- **OpenHands explicit-only skills are flagged as model-invocable** - OpenHands CLI 1.16.0 (SDK 1.21.0) has no `disable-model-invocation` field, so with `--category development` the five explicit-only workflow skills are listed among the skills the model may load, and its `invoke_skill` tool can load them. The adapter claimed enforcement was unproven; it now records that it is absent, and an install notice says how to leave those skills out, including from the `~/.agents/skills` root OpenHands shares with other targets. Their bodies still say the workflow must be selected explicitly.
- **Codex reads a project install's rules** - Codex reads `CODEX_HOME/AGENTS.md` and a project's `AGENTS.md` files from the repository root down, never a project's `.codex/AGENTS.md`, which is where project installs wrote the always-on rules. A project install now writes the root `AGENTS.md`, under the header the other hosts that share it use, and retires an earlier install's `.codex/AGENTS.md`, whose category the category guard keeps. A project whose own `AGENTS.md` no agent-surface manifest claims is refused with `UNOWNED_DESTINATION`, as it already is for those hosts. User installs are unchanged. Codex 0.163.0's `debug prompt-input` shows the new document in the prompt.
- **Antigravity CLI applies the plugin's rules** - Antigravity silently discards a `rules/*.md` file whose frontmatter declares no valid trigger, and the plugin's six always-on rules had no frontmatter, so none applied. Each rule now starts with `trigger: always_on`. Antigravity CLI 1.4.2's `plugin validate` went from six errors and zero rules to zero errors and six rules; its nine warnings about skill bodies over its 24,000-byte load limit are unchanged. Run `agy plugin install` again after reinstalling, because Antigravity loads its own imported copy of the plugin.
- **Goose finds project recipes** - Goose looks up a recipe by name in the working directory, `.agents/recipes` and `.goose/recipes`, but project installs wrote the manual commands' recipes to a bare `recipes/` directory, so `goose recipe list` showed none and `goose recipe validate <name>` could not find them. They now go to `.goose/recipes/`, where Goose 1.34.1 and 1.55.0 list all five and validate them. A development or full reinstall prunes the old `recipes/` files.
- **Droid no longer loads every skill twice** - Droid reads `~/.agents/skills` at the same level as `~/.factory/skills`, at user and project scope, and ignores one copy of any name found in both. agent-surface wrote Droid's skills under `.factory/skills` while Codex, VS Code and the other `.agents/skills` hosts wrote the same skills to the shared root, so a profile with both reported each skill as defined twice in `droid doctor` (82 warnings on a full profile) and let skills installed only for those hosts surface in Droid. Droid's canonical and external skills now use the shared `.agents/skills` root; its commands, droids, rules and MCP stay under `.factory`. A skill an earlier install wrote under `.factory/skills` is a moved route: it is retired once its successor is written, including on a category-filtered install, and a skill the user placed there is left alone.
- **Synapse recall filtered by tags** - `memory_recall` with `tags` applied them after cutting the page to `limit`, so a record carrying every requested tag never came back when it ranked below the best `limit` matches of a query or was older than the newest `limit` records of a browse. Tags are now matched in SQL before the limit, so such a record is returned.
- **MCP launcher after a Node upgrade** - the credential wrapper `~/.local/bin/agent-surface-mcp-env` pins the Node that ran the install. When an upgrade removes that path, as Homebrew's cleanup does with its versioned directories, the wrapper on macOS and Linux now falls back to `node` on `PATH` and says so on stderr, as the Synapse and Grimoire launchers already fall back. A `node` older than 20.12, or none, stops it with a line naming what it found. Before, every credentialed MCP server failed to start until the next install. Rerun `install` to regenerate an existing wrapper.
- **npm advisories in the CLI and both MCP servers** - all three packages move their `fast-uri` override from 3.1.6, now inside the vulnerable 3.0.0-3.1.7 range, to 3.1.8. Synapse and Grimoire also resolve `@modelcontextprotocol/sdk` 1.32.1, `proxy-addr` 2.0.8 and `ip-address` 10.7.3, so `npm audit --omit=dev` reports nothing in any of them. Installed servers pick this up on the next `npm run install:mcps`.
- **Install roots reached through a symbolic link** - an install whose root is itself a symbolic link, such as a home directory that points to another volume, was refused with `traverses symbolic link` for every target. The root is now followed like the directories above it; a link below the root still refuses the plan before anything is written.
- **Unreadable install destinations** - an existing config or output file the installer cannot read, such as an MCP config with no read permission, now blocks the plan with a named line like `MCP config .cursor/mcp.json cannot be read (EACCES)`, and nothing is written. An install root whose `.agent-surface` manifest directory cannot be listed or searched, or whose legacy nested manifest cannot be checked, blocks with `MANIFEST_UNREADABLE`. Before, the run ended with a bare `EACCES` error that named no setting.
- **MCP opt-in** — `--category mcps` without `--service` now selects first-party services only; external MCPs such as `pentest-ai` require an explicit `--service`.
- **Install correctness** — `grimoire-index` wrapper resolves the real entrypoint (derived from `package.json#bin`); a missing required pack fails the install (exit 1) non-destructively instead of silently succeeding.
- **Kilo personal rules** - a user-scope install now registers the always-on rules in `~/.config/kilo/kilo.jsonc` as `~/.config/kilo/rules/<rule>.md`. Kilo resolves a relative entry against the project directory, so the `./rules/<rule>.md` entries earlier installs wrote never loaded the installed rules, and loaded a project's same-named `rules/` file instead (Kilo CLI 7.8.8). Rerun a general user-scope `install` to replace them; your own entries stay.
- **Cline user workflows and rules under a redirected Documents folder** - Cline's pre-SDK extension, which 3.x and most 4.x installs run, reads user workflows and rules under the OS Documents folder, while the CLI and the SDK bundle read `~/Documents/Cline`. When OneDrive backs up Documents on Windows, or an XDG `DOCUMENTS` entry points elsewhere on Linux, a user-scope `install` now writes both. Rules under OneDrive's Documents, which the SDK also scans, go only there so they do not load twice, and a Documents folder outside the home gets a `DOCUMENTS_OUTSIDE_HOME` warning instead of a copy. Before, that extension found none of them.
- **Grimoire provenance and lifecycle** - requires explicit attribution, marks Git-less input `uncommitted`, fingerprints complete skill source, cleans failed publication temporaries, and reopens atomic index replacements.
- **Reinstall safety** - cleans exact declared Gemini/VSCodium and adapter-migration routes while preserving outputs still shared with active targets; maintained JSONC, TOML, and YAML libraries preserve unrelated config; Claude Code and Copilot can share the standard project `.mcp.json` route.
- **Synapse cross-project reads** - binds the cursor to the selected project and returns non-mutable cross-project ids, preventing row-id collisions from reaching local `memory_get` or `memory_forget`.

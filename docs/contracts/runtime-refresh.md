This contract is the normative home for selection, notice, ownership and migration rules in this batch. The other documents carry rationale and link here; when wording differs, this file wins.

## Applicability and Canonical Forms

Domain/data and interfaces are **REQUIRED**: JSON registries persist target facts, install manifests persist ownership, the CLI selects operations, and native files are consumed by other products. New database, HTTP API, event bus and account store are **NOT_APPLICABLE**. Existing JSON Schema, parsers and CLI remain the contract technology.

The optional capability extensions `runtime`, `notices` and `qualifications` are defined in `schemas/target-capabilities.schema.json` and stored in `registry/target-capabilities.json`; `npm run check` validates every stored record through that schema and the cross-field checks in `check.mjs`. The design examples for current targets became those stored records. The proposed `devin` runtime record arrives with `RT3.1`, because it cannot validate before a `devin` target exists. The proposed Antigravity runtime record and successor qualification arrive together with `RT2.3`: the record would validate today, but it names client identities that `RT0.3` has not qualified, and the qualification needs a generated `commands` surface. The internal plan-notice shape lives with its implementation in `scripts/agent-surface/notices.mjs`, not in generated host files. No second mutable registry is introduced.

Current owners remain:

- `registry/targets.json` / `schemas/targets.schema.json`: public target ID, implementation/selection state, build/install availability and render tokens.
- `registry/target-capabilities.json` / its existing schema: support, generation, scopes, evidence; the optional `runtime`, `notices` and `qualifications` extend each existing record.
- `registry/*-assets.json`, `rules.mjs`, `targets.mjs`: domain membership and selected producers. No reclassification in this batch.
- `roots.mjs`, `render.mjs`, `targets.mjs`: actual paths and serialization. Metadata describes them but does not dynamically implement a path.
- `install.mjs`: transient plans, preflight, destination ownership, exact owned routes, writes/removals/config merges and manifests.

## Domain Model

### Target and Runtime Identity

A target key is a selector and manifest owner, not an editor brand. It has zero or one runtime metadata record and zero or more qualifications/notices. A build-only exporter need not invent a runtime identity. New extension fields are optional for existing records; omission means **unrecorded**, never active, safe, tested or unsupported by default.

`runtime` requires `product`, `component`, `clients`, `lifecycle`, `recommendation`, `source_url`, and `checked_at`. Clients are unique stable evidence identities, not automatically CLI aliases. Lifecycle is `active | preview | legacy`; recommendation is `standard | evaluate | legacy`. Neither controls selection. Do not infer security eligibility from lifecycle or recommendation.

The existing target `status` enum remains `implemented | planned | deprecated`. This batch deliberately defines `deprecated` as retained explicit compatibility, excluded from build/install `all`; it is not removal. The only new assignment to that state here is `windsurf`, and only under the [cutover invariant](#selection-and-compatibility). OpenHands remains `implemented`. Availability booleans and actual adapters must agree; planned entries without an adapter cannot be selected. `all` exclusions must be listed in the plan/summary, not hidden. No old manifest is pruned merely because its target was excluded.

### Notices

A notice is a source-backed fact with one stable `code`, `kind`, `surface`, `message`, `action`, `source_url`, `checked_at`, and optional `effective_on`. Kinds: `maintenance`, `retirement`, `security`, `compatibility`. Surface is `target` or an existing capability key that the adapter renders as an output kind at some scope; a key that is only merged config, such as `mcp`, or that renders under another kind, such as Goose `recipes`, is not a notice surface. Code is unique within a target. `retirement` requires the announced date. Date parsing uses an ISO date, not a local-time destructive deadline. Keep one code before/after the date; derive wording, not a second stored lifecycle record.

Security notices describe documented advisories, not a machine-evaluated vulnerability verdict for an unknown installed build. Store no affected-range parser, moving channel cache, installed-package inventory or exploit payload. The runtime owner applies the source-linked release procedure in the research ledger before execution. Asset generation does not launch or clear a client.

One notice is derived by the planner from the selected outputs and the resolved install root instead of being stored per target, because its applicability belongs to the operation rather than the target. It uses the same `PlanNotice` shape and code uniqueness; no scope field is added:

- `SHARED_SKILL_ROOT_MANUAL_UNQUALIFIED` (`compatibility`, surface `skills`, source the [Antigravity skills documentation](https://antigravity.google/docs/skills)): the planned writes include a skill whose frontmatter sets `disable-model-invocation: true` under `.agents/skills/`, and the resolved install root is not the operator's home directory. Antigravity discovers that workspace root, documents only `name`/`description` skill frontmatter, and invokes skills autonomously, so the manual-only guarantee is unqualified there. The condition is the destination, not the `--scope` label: `--scope user --dest <workspace>` receives the notice; a home-root user install does not, and opening the home directory itself as an Antigravity workspace is outside this notice. Codex, VS Code, OpenHands and Zed emit such skills today; the predicate is output-based, not a target list.

Three **plan warnings** describe this operation's own paths rather than an external fact, so they are not notices: they carry `code`, target, path and action, have no source URL or checked date, are listed once per path rather than deduplicated per target, and never change the exit status:

- `SHARED_CONTRIBUTION_REPLACED`: a planned write changes a co-owned file whose other owner recorded an `asset_category` the current selection does not include ([Migration](#migration-consistency-and-recovery) step 2). It names the path, each affected owner and its omitted category, and the selection that restores it.
- `LEGACY_FILE_RETAINED`: a route migration kept a differing old file because the native client is proven to ignore that route ([Migration](#migration-consistency-and-recovery) step 4). It names the old path and the operator action.
- `CO_DISCOVERED_MANUAL_SKILL` (from `RT2.3`): a plan installs Antigravity into a workspace whose `.agents/skills` holds, or will hold, protected command skills that other targets write ([Antigravity](#antigravity)). It names the command, its path, every owning target, and whether the copy is installed or pending. Its action: keep manual-only command skills out of workspaces Antigravity opens, or accept that Antigravity may invoke them automatically there.

### Qualifications

Each qualification identifies one `client`, `surface`, `scope`, `platform`, `component_build`, `scenario`, `level`, `outcome`, `checked_at`, `evidence` and `limitations`. A host build may additionally be recorded for IDE-backed harnesses. Levels are `source`, `render`, `discovery`, `task`, `policy`; outcomes are `pass`, `fail`, `blocked`, `not-run`. Level is not an ordinal score: a task result does not prove tool restriction or independent scope support.

`component_build: null` explicitly means no exact build established. A passing discovery/task/policy record requires a concrete build and evidence. Every pass requires evidence; blocked/not-run records require an explanatory limitation. Source evidence can be an official URL; rendering/runtime receipts identify the relevant source revision and durable artifact or published result. Do not commit full prompts, private paths, auth/config dumps, transcripts or secrets. Evidence references must be shareable for the claim; private receipts may be summarized with their limitation rather than linked as if publicly inspectable.

Semantic validation in `check.mjs` also requires: client belongs to `runtime.clients`; surface exists; build labels such as `latest`, `stable` or `unknown` do not count as exact native build identity; no contradictory claim is inferred from missing records. Cross-target shared harness documentation is not a PASS receipt for another client/platform.

## Interface Projection

| Boundary | Input / trigger | Output and behavior |
|---|---|---|
| Registry reader | Existing target key | Existing capabilities plus validated optional extensions; no network or process execution. |
| Plan presenter | Explicit selection, loaded notices and planner-derived notices | Internal `PlanNotice`: target, code, kind, surface, message, action, source URL, checked date, optional effective date. Excludes qualification transcripts and runtime state. |
| `build --dry-run` / `install --dry-run` | Each command's existing flags; build has target/dry-run, install additionally has scope/category/service selection | Render/plan plus selected notices and explicit exclusions. No mutation; invalid size, ownership or migration conflict returns nonzero. |
| `build` | Existing target selection | Validate all selected output before replacing dist; then write generated files. Deprecated outputs are omitted from an all-target build, not deleted from native install roots. |
| `install` | Same flags, existing execution policy | Show notices before mutation; validate the complete selected operation before provisioning, credentials, writes, stale cleanup or config merges. Then existing apply semantics. |
| `doctor` | Existing diagnostic workflow; no new selector flag | May display the same curated notices; do not add unsafe client execution or turn this into a vulnerability scanner. |
| Native files | Canonical source + selected adapter | Only native schema fields/content, not the internal metadata record. No client updates, accounts, schedules or registration databases. |

Messages go through existing human presentation; diagnostics use stderr where the caller has machine-consumed stdout. No new public JSON mode, protocol or error envelope is required. Deduplicate by `(target, code)` per operation. Retirement notices are emitted when the target is selected even when only skills are selected, but must name the affected surface and state that the current selection is unaffected. Other compatibility notices may be narrowed to selected surfaces. Warnings alone do not make an operation fail.

Blocking diagnostics retain the existing `blocked`/error path and nonzero exit. Stable diagnostic labels for the new blocking cases are `OUTPUT_LIMIT_EXCEEDED`, `OUTPUT_INCLUDE_UNRESOLVED`, `UNOWNED_DESTINATION`, `MANIFEST_UNREADABLE`, `MIGRATION_SOURCE_CONFLICT`, `WORKFLOW_SELECTOR_RETIRED` and `CASCADE_TRANSITION_REQUIRED`. A condition blocks when the operator can clear it without giving up another target they keep, by moving an unowned file, repairing a manifest, reconciling a migration source or narrowing the selection; `OUTPUT_LIMIT_EXCEEDED`, `OUTPUT_INCLUDE_UNRESOLVED`, `UNOWNED_DESTINATION`, `MANIFEST_UNREADABLE` and `MIGRATION_SOURCE_CONFLICT` therefore block whenever they apply. The two output labels meet that criterion only because `build`, which renders the full user-scope output with every category, fails on an oversized or unresolvable canonical command before release, so an operator's `all` never meets a limit that only dropping Antigravity would clear; Cascade's global limit is handled by the cutover instead. A condition that no selection of the affected target can satisfy, or that only dismantling another retained target's state clears, blocks only when that target is named explicitly or nothing else is left to install. Within `all` the plan instead lists the target as not applicable or excluded under the same label, naming how to clear it, and the rest proceeds. `WORKFLOW_SELECTOR_RETIRED` and `CASCADE_TRANSITION_REQUIRED` work this way ([Selection](#selection-and-compatibility), [Cascade and Devin](#cascade-compatibility-and-devin)). `SHARED_CONTRIBUTION_REPLACED`, `LEGACY_FILE_RETAINED` and `CO_DISCOVERED_MANUAL_SKILL` are nonblocking plan warnings, not diagnostics. The existing same-run `also planned by` conflict and the same-target category guard keep their current messages. Include target, scope, relevant path/source and corrective action; do not print file contents. No shell execution is used to resolve those labels.

No authorization model changes: the selected operation remains governed by existing user/repo policy. A warning is not an extra consent prompt. A native manual trigger controls automatic instruction loading, not arbitrary filesystem access or OS confinement.

The new preflight checks output representability, destination ownership and migration conflicts. They do not reverse the existing partial-MCP-install policy: a service with an unestablished prerequisite is still excluded while independently valid siblings remain eligible, with the existing nonzero summary behavior. Revalidate final launch/config output after provisioning resolution; do not bypass the new file/conflict checks on that rebuild path.

## Selection and Compatibility

- `--target` and its existing `--runtime` alias remain artifact selection. Do not advertise qualification IDs as runtime selectors.
- Explicit `windsurf` remains addressable throughout. Until the cutover below it stays `implemented`, remains in `all`, and carries the legacy Cascade notice from `RT1.1`; its oversized rules are not yet blocked.
- **Cutover invariant.** `devin` is admitted to `all` in the same change that marks `windsurf` `deprecated`, excludes it from `all`, and enables its blocking size guard. No default `all` selection may hold both harnesses or become permanently blocked by the Cascade global limit, and for a profile without a Cascade overlap (below) none may lose both Cascade and Devin output. A profile with that overlap keeps its Cascade files untouched and gets neither refresh from `all` until the operator performs the named transition. The `windsurf` selector, its installed files and its manifest remain; no manifest is repointed to `devin`. After the cutover, deprecated targets are visibly excluded from `all` before mutation, in both build and install.
- **Build availability.** The build interface always renders the full user-scope output, which exceeds the Cascade global limit. At the cutover `windsurf` becomes `build_supported: false`, and the build selector enforces that registry field in the same change that relaxes the `check.mjs` rule requiring every adapter to be buildable. `registry/targets.json` stays the single source of build availability; explicit `build --target windsurf` reports the target as not buildable rather than writing an oversized file. Supported subsets remain installable: oversized selected rules block, unselected rules do not. A mixed explicit `all,<name>` remains invalid.
- `openhands` stays explicit/all selectable, buildable and installable with byte-identical output in the metadata slice. No retired-target cleanup.
- `codex-plugin` remains build-only through its adapter flag. Excluding deprecated targets does not alter that distinction.
- Standalone category `all` still means the existing general reset; output-kind and domain categories remain distinct and non-mixable. `--service` remains a selection override, not an exact-state fleet allowlist.
- Antigravity commands projected as rules still have `sourceKind: commands`. With existing source-kind OR render-kind matching, both `--category commands` and `--category rules` select them. This deliberate observable change must be documented and tested. It does not imply canonical always-on rule delivery.
- Deprecated workflow output-kind selection must not delete old files simply because the new producer emits `rules`. After the successor release Antigravity renders nothing for the workflow output kind, so a selection naming only that kind lists Antigravity as not applicable with `WORKFLOW_SELECTOR_RETIRED`, naming the supported selector, and deletes nothing. It is refused only when Antigravity was named explicitly or no selected target has installable output: `--target antigravity --category commands-as-workflows` fails, while `--target all --category commands-as-workflows` still installs the targets that render workflows. Skills-only installs retain legacy files.
- Before native proof `devin` stays unregistered; no runtime count increase or implicit installation occurs from this document. After admission, `all` includes it under normal rules.

## Exact Harness Dispositions

### Cascade Compatibility and Devin

`windsurf`: display **Cascade (legacy Windsurf harness)**, upstream lifecycle `legacy`, recommendation `legacy`; target status becomes `deprecated` only at the cutover. Keep manifest identity and old native routes; this batch transfers no ownership. Never describe Desktop 3.10.35 as running Cascade. Do not recommend installing an old vulnerable desktop solely to retain this adapter.

Cascade limits: the global rule file allows 6,000 characters and each workspace rule file 12,000. Full user-scope general output (9,539 measured) and any development selection exceed the global limit; project general output fits one workspace file, project development output does not. After the cutover the supported response to an oversized selected output is a prewrite block with unchanged old state. Project partitioning, skill references and enterprise machine rules are not substitutes, and project partitioning is not scheduled in this batch because no retained-user need is established. An explicitly selected skills-only operation still works and must not claim full-policy delivery.

`devin`: one new artifact target, display **Devin Local/CLI (shared local harness)**. Client evidence IDs `devin-local` and `devin-cli` are distinct. First admission is the documented CLI surface; Desktop Local remains unqualified until its own check. `C` means the platform's documented config directory, including AppData on Windows and verified XDG overrides where applicable.

| Source | Candidate native destination | Required semantics |
|---|---|---|
| Always-on rules | User `~/.devin/rules/agent-surface-<id>.md`; project `.devin/rules/agent-surface-<id>.md` | Complete per-source native rule. Windows home-rule discovery is a pre-admission probe, not assumed from POSIX. Do not also emit `C/AGENTS.md`. |
| Skills and companions | `C/skills/<name>/...`; project `.devin/skills/<name>/...` | Native directory package; no extra compatibility copy. |
| Manual commands | Same skill roots | Native `triggers: [user]`; preserve command identity; no added permission grants. |
| MCP | `C/mcp_config.json`; project `.devin/mcp_config.json` | Existing `mcpServers` merge contract, current versioned path; preserve `mcp_config.local.json` and general settings. |
| Custom subagents | Not generated in first admission | Omitted model is not parent inheritance; resolve model/tool semantics separately before adding a producer. |

Same-path ownership follows the installer-wide predicate in [Migration](#migration-consistency-and-recovery) step 2. Devin and Cascade also co-discover names at different paths, which that predicate cannot see. Every Devin plan, and every `windsurf` plan for a profile that already holds Devin output, inspects the Cascade surfaces Devin co-discovers, not whole home contents. The surfaces are the set `RT0.2` records: at least the Cascade rules aggregate for that scope when it carries agent-surface's generated header and Cascade MCP server IDs, plus any other surface it finds imported, such as `.codeium/windsurf/global_workflows/` command copies. A surface counts only when the other harness plans, or already holds, the matching kind: the aggregate against Devin rules, server IDs against the same Devin servers, command copies against Devin commands. The check reads that state directly, so deleting a manifest does not clear it. Such state, existing or planned by the same run, is a **Cascade overlap**, labelled `CASCADE_TRANSITION_REQUIRED`. The transition that clears an existing overlap is removing those Cascade files and server entries; a `windsurf` plan that would create one is cleared by narrowing its selection. This batch automates neither. An explicit Devin selection with an existing overlap blocks, as does an explicit `windsurf` selection that would create one on a profile holding Devin output, and an explicit selection of both whose plans would create one, fresh profiles included. Within `all`, Devin is listed as excluded under that label, naming the transition, without changing the exit status, and the rest of the selection proceeds. After the cutover `all` never selects both harnesses. Do not globally disable vendor imports to manufacture a clean test.

The initial release supports fresh nonconflicting Devin installation, not automated Cascade-to-Devin ownership transfer. That transfer is a later exact managed-file operation after loader proof. The old profile remains untouched; operator-authored files are never adopted.

### Antigravity

Keep `antigravity` and `antigravity-cli` distinct. The first successor release extends the former's shared IDE/2.0 customization contract only; it does not clone all CLI features or claim whole-product parity.

| Item | Contract |
|---|---|
| Skills | User base `~/.gemini`, relative `config/skills/<name>/...`. `--scope project --dest <workspace>` already writes the workspace `.agents/skills/<name>/...`, Antigravity's documented workspace skill root, without qualification; it also writes `antigravity/global_workflows/*.md` there, which is not a documented workspace workflow root. `RT0.3` qualifies the project root; the successor keeps the skills route and replaces those workflow files with project manual rules. |
| Manual commands | Native rule at user `config/rules/agent-surface-manual-<name>.md`, project `.agents/rules/agent-surface-manual-<name>.md`; YAML `trigger: manual`, description, full body. |
| Invocation | Explicit rule selection through `@`; do not print a `/name` workflow promise or depend on undocumented skill flags. Native proof is required per product. |
| Limit | 24,000 UTF-8 bytes after native include expansion. Generated command rules must not introduce includes to evade the limit. If existing content uses Antigravity's documented include syntax, resolve it accurately or block as `OUTPUT_INCLUDE_UNRESOLVED`; never count raw bytes alone. Only that documented form is an include: an `@` inside an email address is text. |
| Legacy | Preserve exact currently manifested and `registry/legacy-owned.json`-listed workflow paths on full and partial installs, including the former `antigravity/.agent-surface/antigravity-manifest.json`. Emit no new workflow after the qualified successor release. Before then, warn and retain current behavior without claiming the old path is current-qualified. |
| CLI | Plugin staging/registration, agents, rules and MCP remain its separate contract. No automatic registration or runtime-owned cache edits. |

Keep `commands-as-workflows` in capability history with `generation: not-generated` after the migration, and add a `commands` capability describing native manual rules. Generated tokens become `skills`, `rules`, `external`; do not add a new source kind or imply canonical always-on rules are now emitted.

Do not run `/migrate-workflows`: it enables autonomous skill use. Ordinary manual-rule prompts must not load the protected command; explicit selection must load it. These acceptance criteria apply to a clean profile, where Antigravity's own files are the only copies of the protected commands. In a co-installed workspace, other targets' manual-only skill copies are listed as `CO_DISCOVERED_MANUAL_SKILL`; whether Antigravity loads them autonomously is recorded as `RT0.3` evidence and is not an `RT2.3` failure. Use a harmless bounded task, never a real release/destructive command merely to test invocation. The metadata-only warning ships before this acceptance and is not blocked by unavailable GUI access.

Workspace shared root: manual-only command skills from other targets in a workspace `.agents/skills` are visible to Antigravity without established support for their manual-only flag. The nonblocking `SHARED_SKILL_ROOT_MANUAL_UNQUALIFIED` notice from `RT1.1` covers every such write outside the home install root. Antigravity's own project route makes no such write: it puts only model-invocable skills in `.agents/skills` and writes its protected commands as workflows, which the retirement notice covers. For the protected command IDs being migrated, `RT2.3` adds a semantic preflight beyond equal-path checks: it evaluates the discoverable set in the roots the selected Antigravity product actually co-discovers (retained files, existing artifacts and every selected target's pending outputs, not an unrelated whole-home scan) and lists each protected command skill found there as a `CO_DISCOVERED_MANUAL_SKILL` warning before mutation, even when the destination was initially empty. It does not block: the hazard is unqualified rather than demonstrated, and a block would permanently refuse `--target all --scope project --category development`, where Antigravity and the manual-skill writers always share that root. If `RT0.3` demonstrates that Antigravity invokes a `disable-model-invocation: true` skill autonomously, whether to block, or to move manual command skills out of the shared root, becomes a separate recorded decision. A new manual rule's namespaced filename is not permission to change which semantic command a user invokes. Do not silently rewrite/delete/rename another target's files, drop any target from `all`, disable imports, or weaken the manual-only claim. Existing operator execution policy remains unchanged.

Legacy retention applies even when no current manifest exists. Current manifest entries remain carried forward; legacy-listed files retain their registry provenance without fabricated source revisions or automatic adoption of other files. The former manifest is a nested legacy manifest: its recorded paths count as claims ([Migration](#migration-consistency-and-recovery) step 2) but never authorize removing anything. Legacy archival is outside this batch: no recursive directory deletion, `.bak` convention guessed from a vendor tool, or date-triggered cleanup. A repeated install must retain the same legacy ownership and make no further migration change.

### OpenHands and Other Mappings

OpenHands metadata names **V1 CLI (legacy; retained)**. No path, token, scope, source or MCP change is bundled with recommendation. Canvas/SDK require future independent targets/contracts, not an alias.

Poolside corrects personal output to the documented config-home `AGENTS.md`; project `AGENTS.md` keeps its path, and its header becomes target-neutral in `RT2.0`. ## Migration Consistency and Recovery

This is a bounded set of checks and exact adapter transitions, not a generic migration engine. Declare exact old/new routes beside the affected adapters. Keep the existing manifest shape and `asset_category`; no new content hash, backup store, database or transaction log is introduced.

1. **Render, filter, validate.** Render, apply effective category and scope selection, then validate that selected output set. Current producers run eagerly; pure measurement may happen during rendering, but an unselected oversized output must not throw a blocking error there. Build selects its existing full user-scope output and validates before deleting dist; install validates after filtering and before provisioning, secret collection or filesystem changes.
2. **Destination ownership (every whole-file output, not only migrations).** A manifest records management ownership of a path; it does not reserve a separate per-target policy inside one physical file.
   - **Claim sources.** This target's previous manifest; its `registry/legacy-owned.json` entries; every other `<id>-manifest.json` file directly inside the same resolved install root's `.agent-surface/` directory; and the outputs recorded inside every legacy-listed nested manifest present in the install root, rebased to that manifest's own root and attributed to the target the registry lists it for (for example, Copilot's pre-`146d8e8` `…/Code/User/.agent-surface/copilot-manifest.json`). Retired and unknown target IDs still count as claims. Other files in that directory are not manifests, and manifests under other install roots are not consulted. A nested-manifest claim establishes ownership and cleanup retention only: it never authorizes removing the files it records, which stay in place when the nested manifest itself is cleaned up as a legacy path. That cleanup lists each recorded file left on disk with no remaining claim, so its release is visible. An unparsable or structurally invalid manifest blocks the plan as `MANIFEST_UNREADABLE` instead of being treated as absent or partly absent. Invalid means a `managed` value that is not an array, an entry without a safe relative `output`, a `config_entries` value that is present but not an array, or a config entry without a string `path`, a string `format` and an `ids` array.
   - **No claim.** An existing file at a planned output with no claim is `UNOWNED_DESTINATION`, byte-identical files included. An unowned path is never recorded in a manifest; the operator moves or removes it and reruns. A lost manifest therefore requires removing its files before reinstalling; no adoption flag is added in this batch.
   - **Identical bytes with a claim.** Skipped. The path becomes co-owned when the claim belongs to another owner.
   - **Differing bytes with a claim.** The requested selection regenerates the file; another owner's claim is not a veto. The existing same-target category guard still applies to this target's own partial installs. When another owner recorded an `asset_category` for the path that the current selection does not include, the plan lists `SHARED_CONTRIBUTION_REPLACED` and proceeds, so a general reset stays possible. As in step 3, owners taking part in the same run are judged by their next manifests and other owners by their manifests on disk. Known limitation: the kept same-target guard can refuse a joint partial run, such as `--target droid,openhands --category rules` after a Droid development install, whose end state the same targets reach one at a time; run them separately or reset Droid first.

   All targets that write the shared project `AGENTS.md` render the same target-neutral title and label, so co-selected targets plan identical bytes and a joint install or reset needs no winner. The existing same-run `also planned by` conflict still refuses genuinely differing planned bytes. Config merges keep their existing key-level contract and are outside this predicate.
3. **Cross-owner stale retention.** A stale managed path is retained, and reported as retained, while an owner outside the removal still claims it: a manifest not participating in this run, or a participating plan's next manifest. The removing target drops only its own claim; the file is deleted when no claim remains. Because participants are judged by their next manifests, two participants that both stop claiming a path both remove it; neither retains it for the other.
4. **Owned route migration (Poolside in this batch).** Remove an owned old route only after the replacement write succeeded and only when the old bytes equal the content the current selection renders for the replacement. Otherwise the old bytes may carry edits or an earlier rendering:
   - When the selected native client is not proven to ignore the old route, `MIGRATION_SOURCE_CONFLICT` blocks before mutation, because retaining it can duplicate policy. The operator reconciles the old file, then reruns.
   - When a recorded qualification proves the client ignores the old route, write the replacement, keep the old file and its manifest entry, and list `LEGACY_FILE_RETAINED`. The declared old route is handled only by this rule, never by generic stale cleanup, so the warning repeats until the operator removes the file.

   The adapter's route declaration cites the qualification that establishes an ignored route; without it the route is treated as possibly discovered. No automatic prose merge.
5. **Antigravity legacy retention.** Retain old workflow entries/files from both the current manifest and the explicit legacy-ownership registry, including the former manifest; do not classify them as stale. Archival is outside this batch. Other ordinary stale cleanup is unchanged.
6. **Apply.** Before the run's first write, removal or config merge, write every participating plan's pending manifest, whose managed paths and config entries are the union of that plan's previous and next manifests, through the current atomic replacement; a path in both keeps its next entry, including its `asset_category`, and a config entry keeps the union of both entries' IDs. Writing all of them first keeps a path that one participant releases and another newly claims claimed at every point of the run. Apply the valid plan through existing machinery, then write the final next manifest the same way. Idempotency means a successful repeat changes neither content nor ownership.
7. **Late failure.** A late I/O failure can leave partial writes; the installer has no multi-file transaction. Return nonzero, identify completed/pending paths without content, and do not claim rollback. The pending manifest claims every planned write and every planned removal recorded in either manifest; planned removals of legacy paths stay claimed through `registry/legacy-owned.json`. A rerun of the same selection therefore proceeds without manual deletion.

Deleting an entire profile, changing sign-ins, disabling imports, renaming another target's manifest or restoring an affected runtime version is outside these operations. No client downgrade is an asset rollback.

## Validation Ownership and Proof Gates

- Ajv owns structural types, required fields, enums, date/URI formats and conditional evidence requirements.
- `check.mjs` owns target/client/surface references, unique notice codes, valid renderer/token agreement, build-availability agreement and the distinction between exact build and a channel label.
- Pure roots/renderers own path/syntax and complete size measurement; the planner/build entry point applies blocking size checks only to the effective selected outputs. If the native character unit is undocumented, conservatively require both Unicode code-point and UTF-16 counts to fit and report both plus bytes; do not call this exact host emulation.
- Installer preflight owns real destination/ownership/conflict/selection/no-mutation checks. Use disposable real files and the actual planner/apply entry point. Network/mock runtime responses cannot qualify a native loader.
- Runtime qualification owns discovery, task behavior and policy enforcement. A recorded successful tool read and resulting artifact can prove a task; assistant narration cannot. A tool-list response does not prove a useful operation or restriction.

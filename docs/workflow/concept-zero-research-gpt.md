# Development workflow policy for AI coding agents as of 20 November 2026

## Executive conclusion

The best-supported default is **not** “always TDD,” “always write a spec,” “always use subagents,” or “one prompt to PR.” The most defensible default in late 2026 is an **adaptive, single-agent, closed-loop workflow**:

> **Define the desired outcome and acceptance evidence → inspect only the context needed → implement → run the cheapest verification that can actually observe the likely failure → repair from that evidence → stop when the acceptance condition is met.**

Planning, test-first development, visual prototyping, reviewers, and parallel agents should be **conditional escalations**, not permanent scaffolding. This conclusion is unusually well supported by 2026 evidence: controlled harness ablations find that planning’s value depends on model capability rather than being universally accuracy-improving; a 1,116-application controlled study finds that verification helps only when its “surface” can observe the actual failure mode; a 2,124-run controlled concurrency study finds parallel subagents usually consume 1.41–3.31× the tokens and increase wall time, with gains concentrated in the longest tasks; and a 116-task reviewer experiment shows that a second model can either improve a weaker writer by 18.1 percentage points or *reduce* a stronger writer by 8.6 points. citeturn986376view3turn923151view5turn986376view1turn986376view0

This is also broadly consistent with current product guidance rather than being specific to one CLI. OpenAI’s 2026 Codex guidance describes a loop of planning where warranted, editing, running tests/build/lint, observing, repairing and repeating; its Goals guidance makes the **verification surface and completion condition** first-class. Current Claude Code documentation recommends plan-before-execute for complex work and parallel sessions for genuinely separate tasks, while OpenCode exposes separate Plan and Build agents and isolated subagent contexts. Factory’s current product architecture similarly treats planning, implementation, testing and review as distinct stages, and its Missions product reserves multi-agent decomposition for large projects rather than every edit. These are vendor recommendations, not causal evidence, but they converge with the controlled studies. citeturn403676search1turn403676search4turn403676search5turn410574search7turn953666search0

**Evidence-strength labels below:** **High** means recent controlled or matched experiments with substantial samples and direct workflow manipulation; **Moderate** means peer-reviewed or controlled evidence with limited task domains/sample sizes, or several converging studies; **Low** means case study, observational evidence, vendor experience, or extrapolation. Evidence dated before **20 November 2025** is explicitly marked **OLD**; results tied to superseded models are also flagged rather than silently generalized.

## What the measured evidence says about each workflow

### One-shot implementation followed by verification

A literal “generate once, run tests once, return” workflow is attractive for bounded work because it minimizes inference and coordination cost, but **the evidence supports the verification part much more strongly than the “one-shot” part**. In the 2026 controlled verification-surface study, 1,116 generated web applications were produced across six models and eight tool configurations. About one in seven applications failed to boot when the agent had no checking tools; a simple boot probe removed almost all such failures at roughly 35% of the token cost of giving the agent a full shell. A full shell, meanwhile, cost 2.35× the no-tools condition. The important causal result was not “more tools is better,” but “a checker only helps when it can see the relevant failure.” citeturn923151view5

That favors **implement → cheapest relevant check → repair if necessary** for small tasks. It does *not* justify repeated generic reflection. MACBench found runtime-feedback repair increased checklist success by an average 10.4%, but excessive repair attempts sometimes made final functional outcomes worse by introducing regressions. citeturn413095search4

Typical failure modes are undetected edge cases, validation that cannot observe the true requirement, and declaring success after a shallow green check. Required tooling is minimal: focused tests, compiler/type checker/linter where relevant, a boot/smoke check, and diff inspection. The token and wall-time cost is the lowest of the serious workflows, which is why it is the appropriate base case rather than a multi-agent pipeline. citeturn923151view5turn986376view1

### Test-first and execution-driven TDD

This is the strongest specialized workflow when a trustworthy oracle can be established. At ASE 2026, TDDev evaluated 20 diverse full-stack applications across multiple backbones, two coding-agent implementations and three TDD protocols. With sufficiently capable models, TDD improved accuracy by **15.5–23.7 percentage points**. Whole-project TDD had the best cost efficiency in most conditions; incremental TDD was useful where bounded control mattered; agentic TDD worked best with more capable backbones. A weaker tester could erase the gain, and replacing it with a stronger tester restored it—direct evidence that **oracle quality, not merely “doing TDD,” is causal to the benefit**. citeturn923151view0

TDFlow supplies complementary repository-repair evidence. Its workflow separates patch proposal, debugging, revision and optional test generation into constrained roles; with **human-written tests**, it reported 88.8% on SWE-bench Lite and 94.3% on SWE-bench Verified. The authors manually inspected 800 runs and found seven instances of test hacking, counted as failures. They identify writing valid reproduction tests—not solving them—as a major remaining difficulty. citeturn923151view1

Therefore “TDD everywhere” is too broad. It wins when behavior has a crisp executable oracle: APIs, parsers, transformations, numerical routines, reproducible bugs, migrations with invariants, and browser flows with trustworthy acceptance scripts. It loses when requirements are subjective, when the test writer does not actually know the intended behavior, when the implementation can game or rewrite its own oracle, or when test infrastructure is more expensive than the change. The high-cost failure mode is **overfitting to an invalid or incomplete test suite**. citeturn923151view0turn923151view1

### Spec or plan, then execute

The most useful recent result is not a vendor anecdote but the September 2026 harness-ablation study. Across **176 matched settings**, four models, SWE-bench Verified and Terminal-Bench 2.1, planning shifted roles with model capability: it helped weaker models stay on trajectory and reach an edit, whereas for stronger models it mostly **reduced redundant work and cost with little accuracy change**. This argues against both “planning is mandatory” and “strong models no longer need plans.” It is better understood as an adaptive control mechanism. citeturn986376view3

A separate September 2026 planning study compared four planning surfaces on two models and three tasks, producing 24 scored cells from 48 planning/execution legs. Its conclusions are suggestive—spec-driven and CLI-driven approaches were close, with task-specific winners—but **N=3 task types is too small to establish a universal winner**. It is best treated as supportive rather than decisive evidence. citeturn920438search3

Current OpenAI internal practice provides a useful but non-controlled engineering case study: its agent-first Codex team reports working depth-first through design/code/review/test building blocks, with testing, review, feedback and recovery encoded into the repository; it explicitly warns that the resulting autonomy depends on that repository’s unusually agent-legible tooling and should not be assumed to generalize. Current Codex guidance recommends native Plan mode for larger tasks and verification after milestones; Claude Code documentation likewise recommends planning locally before autonomous cloud execution for complex work. citeturn403676search0turn403676search1turn403676search5

Planning therefore wins when the change has multiple interacting files, external constraints, non-obvious sequencing, irreversible steps or ambiguous architecture. It loses on low-novelty, one-location changes where plan generation merely repeats the request. Required tooling is cheap: read-only exploration, a plan artifact or task list, acceptance criteria and source control checkpoints. Its human-attention cost is mainly **up-front review of assumptions**, which can be far cheaper than reviewing a wrong large diff later; that latter comparison is plausible engineering logic, not a directly quantified 2026 causal result.

### Frontend/prototype first and spike-then-rewrite

For frontend work, the important distinction is that the correctness oracle is often **rendered behavior**, not source text. Vision-guided iterative refinement used a VLM critic on WebDev Arena requests and achieved up to a **17.8% quality increase over three refinement cycles**. The verification-surface experiment separately found that screenshots help specifically on mistakes that are visible—layout and interaction—but add nothing for hidden performance properties such as smoothness over a 100,000-row list. citeturn923151view6turn923151view5

This supports a concrete frontend workflow: build the smallest interactive/rendered artifact that exposes the uncertain requirement, inspect it with browser automation/screenshots, refine the product requirement and implementation together, then add functional and nonvisual tests. Asuka-Bench reinforces the rationale: its 50 web tasks deliberately begin with underspecified intent and use multi-round rendered feedback, yet even the strongest model finished only 52% after three rounds. citeturn413095search7

The stronger claim—**“always spike and throw the code away”**—does not have strong comparative agent evidence. CHI 2026 research reports that practitioners use AI cloud-development environments heavily for rapid prototyping and often regard early frontend artifacts as disposable, but this is observational/qualitative evidence about practice, not a randomized comparison of rewrite versus hardening. citeturn939502search6

Accordingly, prototype-first is recommended for **requirement discovery**, while spike-then-rewrite is only weakly supported as a production engineering rule. Typical failure modes are polishing an architecture that should have remained disposable, mistaking screenshot similarity for behavioral correctness, and allowing prototype shortcuts to become permanent. Tooling should include a real browser, screenshots/DOM access, automated interaction, accessibility checks and functional tests. citeturn923151view5turn923151view6

### Review agents, cross-model gates and parallel multi-agent execution

“Use another agent to review everything” is contradicted by the best direct experiment I found. On **116 matched LiveCodeBench tasks**, GPT-5.5 solo scored 71.6%; Claude Opus 4.7 review raised those drafts to 89.7%, while GPT-5.5 self-review raised them to 84.5%. But Claude Opus 4.7 solo was already at 91.4%; Claude self-review remained at 91.4%, and GPT-5.5 reviewing Claude reduced performance to 82.8%. The positive GPT→Claude gate cost an additional **$0.25/task and 74 seconds**, while GPT self-review cost **$0.12 and 29 seconds**. Claude self-review added 72% to cost and 58% to latency for zero accuracy benefit. citeturn986376view0turn928930view0

These numbers are **model-version-specific**—Claude Opus 4.7 and GPT-5.5, both already superseded or at least not safe proxies for every November 2026 model configuration. The transferable result is narrower: **review value depends on residual error and reviewer capability; a second pass is not inherently beneficial**. The paper itself cautions against generalizing its exact ordering beyond those versions and tasks. citeturn928930view0

Parallel implementation has a still clearer default. The October 2026 dynamic-concurrency study ran **2,124 executions over 354 tasks** with native concurrency switched on/off for Codex, Claude Code and Kimi Code. Token consumption rose to **1.41–3.31×**, runtime increased in **14 of 15** agent×benchmark combinations, and concurrent Codex consumed 24.12 million recorded tokens per solved task versus 7.69 million sequentially. Concurrency was at least 20% faster in only 46 of 366 cases solved in both modes. Benefits rose with task horizon and were best on LoopsBench; bounded SWE-bench tasks received no consistent gain and sometimes large losses. citeturn923151view4turn986376view1

The positive counterexample is **structured** multi-agent engineering, not free-for-all spawning. CAID uses a central dependency-aware manager, isolated git worktrees, asynchronous engineers, explicit merge integration and executable verification. On long-horizon PaperBench and Commit0 it improved over the single-agent baseline by about **25.6 and 14.7 percentage points**, respectively, in the final COLM report. citeturn123443search0turn123443search4

The dividing line is therefore not “single versus multi-agent” but **whether the task genuinely contains parallelizable work and whether isolation/integration machinery exists**. Typical failures in unstructured concurrency are duplicated exploration, overlapping edits, load imbalance, subagents terminating before integration and budget exhaustion; the 2,124-run study explicitly observed coordination and scheduling failures at scale. citeturn986376view1

## Recommended default

The default I would encode into Claude Code, Codex CLI, Droid, OpenCode or a comparable late-2026 coding harness is:

**Single agent, explicit outcome, minimal sufficient context, implementation, evidence-producing verification, bounded repair.**

Concretely, the agent should first express—not necessarily in a user-visible essay—the **completion condition, relevant constraints and verification method**. For a trivial edit this can be implicit and take seconds; for a meaningful change it should be a short task contract. It should then inspect the narrowest plausible code surface, implement the change, run the cheapest verifier capable of exposing the likely failure, and repair from actual failures. It should expand context, planning depth, tests or agent count only when the observed trajectory shows that the simpler mode is insufficient. This combines the strongest causal findings from verification-surface experiments, harness ablations and concurrency studies without paying the fixed overhead of their heavier alternatives. citeturn923151view5turn986376view3turn986376view1

This default differs from “one-shot implement then verify” in one important respect: **failure automatically creates another evidence-driven implementation cycle**. It differs from mandatory TDD because tests are elevated to first-class steering mechanisms only when they are trustworthy and cheap enough. It differs from mandatory planning because planning depth is proportional to task structure. And it differs from agent teams because parallelism has to justify its coordination cost rather than being treated as free intelligence. citeturn923151view0turn986376view3turn986376view1

It also maps well onto the current CLI architectures. Codex’s 2026 Goals framework explicitly asks for an outcome, verification surface, constraints, boundaries, iteration policy and blocked stop condition; OpenAI’s long-horizon guidance implements plan/edit/test/observe/repair loops. Claude Code’s current cloud guidance recommends planning complex tasks before execution and uses isolated sessions for independent parallel tasks. OpenCode separates Plan, Build, Explore and reusable reviewer subagents. Those are implementation conveniences, not evidence that the products themselves outperform one another. citeturn403676search4turn403676search1turn403676search5turn410574search7
